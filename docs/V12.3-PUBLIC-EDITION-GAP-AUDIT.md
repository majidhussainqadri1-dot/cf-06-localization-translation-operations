# CF-06 — V12.3 public edition policy: code and remaining acceptance

Requirements source: Sabri Website Master Plan V12.3 (13 November 2026), pages 51–53 and 248–256.
Scope: **one canonical author original plus nine distinct, approved, source-linked language editions**, reviewed and published only by appropriate owners.

## Confirmed predecessor gap

The October 2026 RC5 candidate has locale registry, translation units, versions, approved content links, rollback and source-staleness handling. It does NOT prove V12.3's new nine-target/reserve selection, approved Chinese script, independent current-edition count, or File 20/21/26 production interoperability. Three first-class UI locales are not nine approved content targets.

## Implemented in this isolated source patch

- Pure PublicEditionPolicy validates a versioned, effective-dated policy with an explicit approval reference, exactly nine unique primary targets, independently selected Chinese script, and bounded declared reserves and aliases.
- Duplicate/ambiguous locales and alias chains fail closed. The canonical original is excluded from its own translation targets and the first distinct reserve is used. An insufficient reserve yields an explicit blocked result rather than a fabricated edition.
- Planning requires a separate independent-approval boolean; no claimed approval reference alone can authorize anything. The LocaleService integration obtains this only from the deny-by-default filter slto_verify_founder_edition_policy.
- The report of CURRENT approved public editions only counts matching source version, SHA-256, HTTPS URL, public/published status, distinct locale, and per-record independent owner attestation through slto_verify_current_edition_publication. No real owner attestation means zero verified editions.
- The existing REST namespace exposes a privileged, bounded, read-only POST /edition-policy/preview for planning evidence. Neither this route nor the new service creates jobs, approves a translation, publishes, contacts a provider, enables a capability, or grants authorization.
- Machine-readable PlanCompliance distinguishes UI, preferred content language, and the edition of the currently viewed object. File 20 still owns the actual UI state and switcher.
- New adversarial test suite tests nine-target uniqueness, source alias, reserve shortfall, malformed locale, Chinese script, no approval, stale public proof, private record, HTTP URL and all-ten verified synthetic versions.

The five additional languages and reserves used in unit-test fixtures are synthetic examples **ONLY**, not Founder-approved language decisions.

## Second bounded source correction — publication URL pair

Confirmed source gap: ContentLinkService::register previously accepted publication_status=published with a null translated_url and/or canonical_url, contrary to V12.3 page 52 and CF06-FR-028. PublishedUrlGuard::assertValid now denies absent, non-HTTPS, credential-bearing, fragment or oversized publication URLs before any DB or outbox write. Unpublished draft/review/approved records remain allowed to omit URLs. Existing same-origin verification and independent native owner approval stay intact.

Eight domain positive/negative tests and one source-wiring-order test are included in mandatory CI. This is repository-only correction, not a verified Live incident or deployment.

## Additional adversarial source review: false public-edition count

During source review, PublicEditionPolicy::countVerifiedPublished initially allowed two distinct locales to count against an identical public URL and did not independently require the canonical URL in the counting predicate. This is inconsistent with V12.3's distinct source-linked publication URLs and approved canonical search metadata. The bounded source fix requires current public HTTPS + canonical HTTPS fields, rejects credentials/fragments, and prevents exact duplicate public-URL counting. Two new negative tests cover the duplicated URL and absent/insecure/fragment canonical URL.

This is a source candidate fix and automated review, NOT independent File 21/26 publication proof, not a fresh real public site check, and not an independent external release review. Regional canonical preferences still require real File 26 evidence; duplicate URL canonical-equivalence across encodings is not certified by this exact-string guard.

## Cross-project translation job concurrency — repository correction

Previous source inserts a unit for each (project_uuid, resource_uuid, target_locale). The SQL uniqueness index did **not** prevent a second active project from creating the same source-version + target-locale job. This is a genuine repository-source gap against V12.3 page 52; it is not verified as a Live production defect.

The added **TranslationJobConcurrencyGuard** runs **inside** the same transaction used by ProjectService::create. It verifies **all three** relevant tables use InnoDB, locks all canonical resource rows in a stable UUID order using SELECT ... FOR UPDATE, checks source locale/version/hash are unchanged, and checks for any active unit in an active/draft/paused project with the same canonical source version/hash and any requested target. It aborts with an explicit 409 logical conflict before inserting a project or unit. Cancelled/archived projects, released/retired/stale units and new source versions do not permanently block legitimate future work.

This uses existing tables without a schema-version bump or migration. **Caveat:** the proof covers only creators entering the canonical ProjectService and sharing the same CF-06 resource UUID. File 21 and other module owners must obey this contract; duplicate File 21 originals mapped to different CF-06 resource IDs cannot be resolved by CF-06 without a canonical owner mapping.

Disposable MySQL/WordPress integration: tests/wp-v123-project-uniqueness.php creates synthetic locales/resources, checks initial creation, duplicate rejection, different target acceptance, post-cancellation reuse, and corrected source-version acceptance. All fixture rows are rolled back via the enclosing SQL transaction. A real parallel multi-process stress/soak suite and a Hostinger schema/engine audit remain unaccepted.

## Immutable versioned locale policy candidate registry

V12.3 requires a Founder-approved versioned language-target/reserve register. The new `EditionPolicyRegistry` implements an immutable **registered** revision on WordPress's native options table, keyed by policy ID + revision. It requires current File 00 membership, release capability, step-up authentication, and a separate **deny-by-default independent Founder-approval** filter that receives the complete normalized policy (including target/reserve/aliases). The operation uses one InnoDB transaction for the atomic unique insert and tamper-evident audit. Identical retries read the same immutable revision; different content under the same revision produces a 409 conflict. A stored record never automatically activates the language policy, publishes, contacts providers, or creates jobs.

The privileged REST interface provides version registration, exact revision retrieval and preview of a registered candidate. A stored version is still rechecked against independent Founder approval on preview. Required WordPress/MySQL test cases include negative authorization, missing Founder attestation, first registration, identical retry, exact retrieval, altered-revision rejection, approved read-only preview and post-revocation fail-closed preview. All synthetic policy records and audit events are rolled back in CI.

**Still missing:** actual Founder-selected Chinese script, other five targets and reserve ordering, deployed File 00/20/21/26 policy/SEO contracts, operational signing/approval proof, and a genuinely independent live/staging acceptance. Stored status `registered` means policy recorded with testable external approval, **not active**, not actual translated content. No production policy was registered in this coding session.

## Reciprocal hreflang, canonical and search-proof evidence

New `PublicEditionGraphAuditor` with a separately authorized `PublicationGraphService` adds a bounded **read-only** audit for current public original and translated URLs. It checks same-origin HTTPS, source-version/hash parity, published/public status, distinct locales and URLs, each page's complete reciprocal `hreflang` mapping, default-denied independent original/translation owner evidence, and an independent File 26 receipt. A same-language regional canonical override may be reviewed only with an actual File 26 proof; cross-language overrides are rejected. No auditing action grants indexing or publication rights. Test fixtures are synthetic only.

The three independent deny-by-default hooks are `slto_verify_graph_original_owner`, `slto_verify_graph_translation_owner`, and `slto_verify_file26_search_graph`. Real File 21/File 26 providers and browser/site evidence are **not installed/verified in this repository**. The report can be structurally promising but is NEVER Live acceptance until independent source and search proofs exist.

## Second privacy review of durable policy metadata

Source review identified unnecessary `registered_by` actor duplication in the WordPress option record. The registry now stores **no independent actor identifier** in `wp_options`; the governance audit already records the actor subject to its retention exception. The Founder approval field is restricted to a bounded opaque non-secret reference, rejecting emails and free text. Negative tests are included. This does not replace live compliance, data deletion or external policy approval.
